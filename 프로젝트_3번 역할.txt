• 3번 역할은 단순히 “GPT에게 장애 원인을 물어보는 역할”이 아닙니다. 이 프로젝트에서는 2번이 만든 패킷 관찰 결과를 받아, 근거·원인 후보·추가 점검 항목을 구조화된 diagnosis.json으로 만드는 역할입니다.

  현재 구현은 이렇게 동작합니다.

  packet_summary.json
          ↓
  규칙 기반 진단기
  ARP → ICMP → DNS → TCP 순서로 첫 실패 지점 판단
          ↓
  diagnosis.json
  (근거, 가설, 확신도, 추가 확인 항목)
          ↓
  선택적으로 GPT가 사람이 읽기 좋은 설명을 추가

  핵심은 03_packet_ai/analyzer.py입니다.

  - 기본 실행: API 없이 규칙 기반으로 진단합니다.
  - --use-ai 옵션 실행: OpenAI API를 호출해 서술형 진단(ai_narrative)을 추가합니다.
  - API가 실패해도 규칙 기반 결과로 자동 대체합니다.
  - 실제 복구 명령은 만들지 않습니다. 복구는 4번 SRE 역할입니다.

  예를 들어:

  - ARP Request는 있는데 Reply가 0개
      - L2 문제 후보: Gateway IP 오류, VLAN 오류, SVI Down, 대상 장비 Down

  - DNS Query는 있는데 Response가 없음
      - DNS 서버 주소 오류, DNS 서비스 중단, 경로 문제 후보

  - TCP SYN 뒤 RST가 옴
      - 서버까지는 도달했지만 해당 포트 서비스가 꺼졌거나 거부한 것으로 높은 확신

  중요한 규칙은 0과 null을 다르게 처리하는 것입니다.

  - 0: 관찰했지만 해당 패킷이 없었음
  - null: 애초에 관찰하지 못했음

  그래서 AI가 “관찰하지 않은 TCP가 실패했다”처럼 잘못 해석하지 않도록 막습니다.

  RAG나 벡터 DB는 현재 프로젝트에 필요하지 않습니다. 이유는 입력이 방대한 문서 집합이 아니라, 2번이 만든 한 건의 구조화된 패킷 요약 JSON이기 때문입니다. 현재 문제는 “어떤 문서를 찾아 답할까?”가 아니
  라 “이 패킷 수치가 어느 계층의 실패를 보여 주는가?”입니다.

  RAG가 필요한 경우는 나중에 다음처럼 범위가 커질 때입니다.

  - 과거 장애 보고서 수백 건에서 유사 사례 검색
  - Cisco/Wireshark/사내 운영 문서를 근거로 답변
  - 장비별 운영 매뉴얼과 변경 이력을 함께 참조
  - 답변마다 어떤 문서를 근거로 했는지 출처 표시

  그때는 문서 수집 → 청크 분할 → 임베딩 → 벡터 검색 → 검색 결과를 GPT에 전달하는 RAG 구조를 추가할 수 있습니다. 하지만 현재 단계에서 RAG를 먼저 넣으면 데이터 준비·검색 정확도·평가 부담만 늘고, 핵심인
  패킷 기반 진단 흐름이 흐려집니다.

  발표 때는 이렇게 설명하면 좋습니다.

  > “3번 역할은 GPT API만 연결한 챗봇이 아니라, 2번의 패킷 관찰 데이터를 ARP·ICMP·DNS·TCP 계층 순서로 검증하는 진단기입니다. 규칙 기반 결과로 안정적인 JSON을 만들고, GPT는 그 근거를 사람이 이해하기
  > 쉽게 설명하는 보조 역할입니다. 현재는 단일 장애 사례의 구조화된 데이터를 다루므로 RAG보다 정확한 입력 계약과 가드레일이 더 중요합니다.”
